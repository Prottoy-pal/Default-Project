# Git workflow

How the copies of this project relate, and the six commands that keep them
straight.

## The daily loop

At the **start** of every session:

```bash
git pull --rebase
```

At the **end**:

```bash
git add -A
git commit -m "short why, not what"
git push
```

That is the whole workflow. `--rebase` keeps history linear and avoids the
merge-commit noise that confuses a reader of the repository.

---

## The rule that prevents 90% of problems

**Pull before you push.** Always. Two copies pushing to one branch will diverge
otherwise, and resolving a diverged history is not a skill worth learning for
this project.

If `git push` is rejected:

```bash
git pull --rebase      # replays your commits on top of GitHub's
git push
```

## Six commands, and when to use them

| Command | Use when |
|---|---|
| `git status` | always first. Shows what is staged, modified, untracked |
| `git diff` | before `git add`, to see what you actually changed |
| `git log --oneline -10` | before committing, to match the message style |
| `git pull --rebase` | at the start of every session |
| `git add -A && git commit -m "..."` | when a unit of work is complete and consistent |
| `git push` | after commit, once, at the end |

---

## Commit messages

Write **why**, not what. The diff already says what.

| Bad | Good |
|---|---|
| `update` | `Add scenario 02: web server, scoped source, default drop` |
| `fixes` | `Restore template header: leading -- made the YAML unparseable` |
| `more work` | `Harness: probe.py handles TCP timeout as drop, not error` |

A commit message is read by: you in March, your supervisor, and anyone who
clones the repo. "update" tells all three nothing.

---

## Never commit

Already covered by `.gitignore`, but state it plainly:

- `results/*.json`, `results/*.jsonl` — raw runs, large and regenerable
- `.env`, any API key — a leaked key in git history is permanent
- model caches, `__pycache__`, `.venv`

The rule of thumb: **if it can be regenerated by running a command, it does not
belong in git.**

## When something goes wrong

| Symptom | Meaning | Fix |
|---|---|---|
| `rejected — non-fast-forward` | GitHub has commits you don't | `git pull --rebase`, then push |
| `Your local changes would be overwritten` | uncommitted work blocks the pull | commit it first, then pull |
| `fatal: not a git repository` | you are in the wrong folder | `cd E:\Half-firwall` |
| `index.lock` exists | a git process died mid-write | delete `.git/index.lock` — only when no git process is running |
| Conflict markers in a file | both copies edited the same lines | open the file, keep the correct version, `git add`, `git rebase --continue` |
| Pushed a secret | it is in history now | rotate the key immediately; do not just delete the file |

## Publishing and citation, once

- GitHub: repository is public, MIT detected, `main` is the default branch.
- Zenodo: connect the repository in Zenodo's GitHub settings, then create a
  release. Zenodo mints a DOI and it appears in `CITATION.cff`.
- After the DOI exists, add it to `CITATION.cff` and `README.md`.

Do this after Gate A, not before. A DOI is for an artifact that already does
something.
